## Diagnostic follow-up 0.1.1

- Adds a narrow YouTube pairing rule: exact `Sponsored` + exact `Send to phone` together. Neither label alone triggers; excluded title/description/recommendation containers are ineligible. This rule cannot help if the labels are not exposed to the app.
- Empty/whitespace-only virtual labels no longer establish a complete meaningful read.
- Debug service dumps report node/empty-label counts and known marker categories; announcement events are observed for diagnosis. Events remain **diagnostic only**, never ad evidence.
- An explicit debug-only screenshot probe uses Android's screenshot API, then discards pixels and retains only brightness counts. It is **not OCR** and does not capture continuously. Its additional screenshot capability exists only in debug resources.
- A debug-only 10-second output test isolates cover/volume handling from the detector. It requires a selected foreground app and keeps normal pause, app-exit, and lifecycle recovery controls.
- Full-screen ad-detection OCR remains unimplemented; the later, narrowly scoped opt-in OCR scans only for explicit Dismiss/Skip controls. Do not bypass protected content or briefly hide the visual cover to inspect ads.

On Android 11 a display screenshot can include the app's dark cover. Android's API for taking an app-window screenshot underneath an accessibility overlay is available from API 34 (Android 14). This is a separate restoration constraint even if the initial ad labels can be captured.

References: [Android screenshot APIs](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService), [local OCR with ML Kit](https://developers.google.com/ml-kit/vision/text-recognition/v2/android).

## October 13 follow-up

- The user confirmed that the explicit 10-second comfort test displayed the grey cover as expected.
- During that test, the user reported ARC audio remained audible. Android logs show ADMute requested media volume 0, followed by system writes at 4 and 3; the final stream state was volume 3/100 and `Muted=false`. The cover test passed visually; the ARC mute test failed.
- Version 0.1.2 adds a native media-stream mute request, verifies Android's reported mute state, and retains zero-volume fallback. Unit tests, lint, and APK assembly pass. Its initial TV run exposed delayed mute-state reporting; the ownership record was kept until release and a delayed-mute regression test was added.
- With the corrected 0.1.2 build installed and accessibility re-enabled, the explicit 10-second output test reported Android `Muted=true` at both the 2-second and 7-second checks; the user confirmed ARC audio stopped. On timeout, ADMute sent `ADJUST_UNMUTE`, Android reported `Muted=false`, and the ownership record cleared. Android changed the media level from 3 to 2 during release; it was restored manually to the pre-test level 3. No mute or saved-volume recovery record remained afterward.
- The current 0.1.2 service sample still has zero meaningful YouTube labels. The new build does not fix or claim YouTube ad recognition.

Audio-command logs distinguish the app's `setStreamVolume(..., 0, 0)` requests from the following system volume writes. This demonstrates failure of the zero-volume strategy on the current ARC route. It does not establish whether a native mute/unmute command will work; that must be a separate device experiment.

## Required gates before another compatibility claim

1. **Audio output:** version 0.1.2's native media-stream mute/unmute command stopped audible HDMI ARC output in an explicit test and unmuted on test release. Verify the same behavior during an automatically recognized ad. Android changed the stream index on unmute in the explicit test; the user's baseline was restored manually. Continue verifying volume and mute restoration on every route.
2. **Detection:** establish that a visible ad frame, including the user-observed markers, can be captured and read on this TV. Empty trees and black captures are UNKNOWN, not evidence of a cleared ad. A successful home-screen capture does not pass this gate. Full-screen OCR has not been implemented or validated.
3. **Visual restoration:** resolve how to observe ad endings while a full opaque cover is present on Android 11. Do not briefly expose the ad to obtain frames. No automatic full-cover restoration guarantee is appropriate while this remains unresolved.

The 25 synthetic tests validate their mocked contracts. They do not model these device-specific ARC callbacks or prove readable YouTube playback pixels. Keep this build paused and the pull request in draft until these gates pass.

## Live service and OCR follow-up · 0.1.7

The owner's screen showed the Enable switch on but the service row Off. The TCL app-start guard explicitly rejected the service bind with `callee_does't_have_OP_AUTO_START_permission`; its ADMute `APP_AUTO_START` operation was `ignore`. Allowing this operation for ADMute and refreshing its own registration resolved binding. The service runs normally and remained bound after the in-place 0.1.7 update.

The replacement Google Play Services recognizer is now **tested as unavailable on this TV**: both OCR module versions were zero, with `No acceptable module found`. It did not crash the service. No automatic Dismiss or Skip action was confirmed. Version 0.1.7 exposes this reason in status instead of letting the polling status hide it and retries model checks once per minute. YouTube still returns UNKNOWN with zero meaningful labels. No end-to-end comfort/ad-control pass is claimed. See the [current live verification](VERIFICATION.md#live-follow-up--017-october-13-2026).
